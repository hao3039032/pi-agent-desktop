# Desktop shell (Tauri) and packaging — fork notes

Fork-owned notes moved out of `AGENTS.md` to keep it short. The upstream doc on the same topic (`docs/agents/*.md` without the `fork-` prefix) may describe the same area in other words; where they disagree, these notes describe this fork. Hard rules that must survive a merge are also listed in `AGENTS.md` under **Hard rules**.

## Desktop shell (Tauri)
- **LW native drop policy:** `useDesktopDragDrop` handles Tauri absolute paths; the HTML5 handler exits on desktop to avoid duplicate imports. Directories insert paths, images use the authenticated path reader, and other files use disk-to-disk import without browser byte caps. Keep the upstream `+` picker using `importProjectFiles`. Non-project Chats accept images only: neither directories nor other files may enter through native drops. Regression guards: `components/ChatWindow.desktop-drop.test.mjs` and `components/composer-file-picker.test.mjs`.
- `lib/desktop-native.ts` is the only place the UI touches Tauri APIs; every entry point checks `isTauriDesktop()` and degrades to a web equivalent. Tauri commands are declared in `src-tauri/src/lib.rs`, their permissions in `src-tauri/permissions/desktop-shell.toml`, and both must be listed in `src-tauri/capabilities/desktop-dialog.json` or the call fails at runtime only.
- `/api/desktop/read-images`, `/api/desktop/save`, and `/api/files?...type=import` deliberately accept absolute paths selected by native dialogs, so the normal `lib/file-access.ts` source/destination allow-list cannot cover them (`save` still allow-lists its *source*). They require a loopback Host, normal request-security checks, and the per-process desktop token from `lib/desktop-api-auth.ts`. The Tauri shell passes the token to the packaged server and exposes it to the trusted WebView through the capability-scoped `get_desktop_api_token` command. Never fall back to a static token or User-Agent detection.
- `read-images` caps the file count at `MAX_ATTACHED_IMAGES` from `lib/image-attachments.ts`. Keep it derived from that constant; a separate literal silently 400s selections the composer considered valid.
- Open a local path with `explorer.exe` on Windows, never `cmd.exe /C start` — Rust's argument escaping does not apply to the cmd parser, so a legal path like `C:\src\R&D\x.txt` would split into commands.
- `lib/app-prefs.ts` owns every fork `localStorage` key; new fork code goes through it. Upstream-owned files (`useChatAppearance`, `useEnterSendMode`, `useResizablePanel`, `thinking-expansion-preference`, `ProviderUsageSummary`, the theme init script) keep their own keys — leave them there rather than adding merge conflicts. Theme is additionally mirrored into the app config dir via the `set_ui_theme` command, because the packaged server's port (and therefore the WebView origin, and therefore `localStorage`) can change between cold starts.
- `tauri build` refuses to bundle when a `tauri-plugin-*` crate and its `@tauri-apps/plugin-*` npm package sit on different major/minor releases (same for `tauri` ↔ `@tauri-apps/api`), and it only says so six minutes into each platform of a signed release. The npm half moves on its own: a sync that runs a plain `npm install` re-resolves the caret ranges in `package.json` and leaves `src-tauri/Cargo.lock` behind — that is how v0.4.7 failed on all three runners with plugin-updater 2.12.0 against crate 2.10.1. Fix it in the lock (`cargo update -p tauri-plugin-updater --precise 2.12.0`), never by pinning the npm range down; `scripts/release-workflows.test.mjs` pins the pairing.
- **File right-click menu** (`hooks/useFileContextMenu.ts`, `lib/file-context-menu.ts`): written-file chips, markdown links to local files and inline code that names an existing file open a native menu — Open (preview pane) / Open With ▸ / Reveal / Copy Path. Open With is macOS-only: `list_apps_for_file` asks Launch Services through `osascript -l JavaScript` (the path is an argument, never spliced into the script; nested bundles and `/Library/Caches/` copies are filtered; for files with a specific type family such as source code or JSON, apps that only reach the file through generic `public.plain-text` claims — Word, Excel, Numbers, Notes — are dropped, keeping the default app and the system text editor; unclassifiable files and an empty result keep the full list), `open_path_with` runs `open -a` and only accepts an existing `.app` directory. Both are declared in `desktop-shell.toml` and listed in `desktop-dialog.json`. Inline code is only a guess, so the handler claims the right-click synchronously, then asks `GET /api/files/<path>?type=meta` (the allow-list applies) — a miss falls back to Copy / Select All, and rendering never stats anything. App lists are cached per extension for 5 minutes, and a lookup slower than 800ms opens the menu with just "Other…". In a browser the handler does nothing.
- **Native popup menus are built and shown in Rust** (`show_popup_menu` in `src-tauri/src/lib.rs`, `lib/desktop-menu.ts`, `lib/desktop-menu-model.ts`). The UI sends a plain-data description (`toPopupSpec`) and gets the picked item id back as the command's result; `onSelect` runs after the menu closes. Do not go back to the JS menu API (`Menu.new` / `menu.popup()`): its menus and items are resources the page holds, tauri 2.12.1 drops an item's click channel once a nested wrapper goes out of scope (every item ignored clicks), and its `popup` command holds the webview resource-table lock for as long as the menu is open, so one IPC call that needs the table in that window deadlocks the app (Settings froze it in 0.6.x). `NEXT_PUBLIC_NATIVE_POPUP_MENUS=0` at build time turns native popups off; every caller then uses its DOM menu (`DomContextMenuHost` for the file menu). Lifecycle lines (`popup #N open/closed/selected`) go to `desktop.log` in the app log dir, so a hang leaves its last step on disk. The `.github/workflows/desktop-test-build.yml` workflow (manual) builds installers for all three platforms as artifacts without publishing, for sending a build to someone to try.
- **Window geometry** is restored by `tauri-plugin-window-state`, registered in Rust only (no npm package, no capability entry) with `SIZE | POSITION | MAXIMIZED`. Never add `VISIBLE` (it would bring back a window hidden to the tray before quit; show/hide is owned here) or `DECORATIONS` (custom chrome). Closing hides the window, so geometry only matters across quit/relaunch; the plugin saves on `CloseRequested` and on `RunEvent::Exit`.
- `lib/workspace-state.ts` restores the last session/cwd/file tabs on cold start. URL params always win over the persisted workspace.
- `useDesktopConnection` polls `/api/home` only in Tauri to drive the offline banner. Its cleanup must stop in-flight probes from rescheduling, otherwise an unmount leaves a timer nobody owns and it pings forever.

## Workspace terminals & node-pty staging
- General's Default terminal picker detects local executables without launching
  a shell. Automatic prefers PowerShell 7, Windows PowerShell, then CMD on Windows;
  macOS/Linux retain the user's executable `$SHELL` and login arguments. The choice
  lives in Pi Web's `terminalShell` preference and applies only to new PTYs.
  A missing explicit choice requires reselection, never a silent replacement.
- Windows ConPTY rejects POSIX signal names. `killTerminal`, including forced
  shutdown, must call `pty.kill()` without a signal on Windows; only Unix uses
  `SIGKILL` and the delayed escalation. The native terminal regression verifies
  actual process startup, reuse and forced closure in an isolated child process.
  Timer and SSE checks use a controlled PTY so mocked timers cannot strand native
  workers; they still exercise the real manager and events route.
- Windows also needs all of node-pty's `lib/`, including `worker/conoutSocketWorker.js`
  and `conpty_console_list_agent.js`. Next tracing omits these computed-path entry points;
  native prebuilds alone produce an empty terminal followed by exit code -1.
  `npm run desktop:verify` now runs an actual shell using the staged Node and node-pty.
- Terminal tabs load `node-pty` through a runtime-computed path (`prebuilds/${platform}-${arch}/*.node`), which Next's file tracer cannot follow — a bare standalone build ships only `lib/` and breaks at runtime. `prepare-desktop.mjs` copies the whole `prebuilds/` tree and chmods `spawn-helper` for **both** darwin variants (macOS strips the bit in published prebuilds; `bin/prepare-terminal.js` fixes the same thing at npm-install time). If terminal tabs 500 or hang in a packaged app, check that `resources/server/node_modules/node-pty/prebuilds/` exists with executable helpers first.
- Code mode's QuickJS sandbox used to load `quickjs-wasi` through runtime `import.meta.resolve` (`quickjs.wasm` + `extensions/*.so`), which the file tracer also cannot follow — the traced output kept only `dist/` and every packaged session lost Code mode with `Cannot find module .../quickjs-wasi/quickjs.wasm`, so `prepare-desktop.mjs` staged the complete package (`stageCompletePackage()`, `scripts/stage-package.mjs`, also used for jiti, which stays staged: the SDK's lazy `require("jiti")` path is broad; never hard-code a nested destination for it — `dedupeNestedPackages()` deletes nested copies whose version matches the top level, which on pi 1.0.1 removed the complete copy and left the traced, incomplete top-level one). Since the CLI-engine migration the sandbox runs inside the bundled pi distribution and nothing in the staged server loads it, so quickjs-wasi is no longer staged. After any SDK bump run `npm run desktop:prepare && npm run desktop:verify`; it starts the staged server with the bundled Node, creates a session over the bundled pi child (whose stderr is relayed into the server log) and fails on any `Cannot find module` there; the distribution's own completeness is the manifest check in `scripts/verify-packaged-frontend.mjs`. It does not cover jiti.
- **Windows overwrite installs never delete old payload** (#72): Tauri's NSIS template only `File /a`s the new files over `$INSTDIR`, so a stale `resources/server/node_modules` survives an upgrade and Node's nearest-module resolution loads a leftover nested `@earendil-works/*` copy instead of the new top-level one — 0.4.7→0.5.1 shipped one and died on `does not provide an export named 'runToolCall'` with every API route 500ing. Three guards, all required: `NSIS_HOOK_PREINSTALL` in `src-tauri/installer-hooks.nsh` (registered via `bundle.windows.nsis.installerHooks` in `tauri.windows.conf.json`, resolved against src-tauri as cwd) clears `resources\server\node_modules` before the installer writes the fresh tree; `desktop/server-launcher.cjs` deletes any `@earendil-works/*/node_modules/@earendil-works/*` at startup, which heals installs that upgraded in place before the hook existed (the build never legitimately ships one — the whole scope is pinned to one version line — while nested non-pi deps like chalk/undici are normal and stay); and `prepare-desktop.mjs` fails the build if a nested pi-scope copy survives `dedupeNestedPackages()`. The dedupe pass depends on the pi-package overlay copying each `package.json` beside `dist/` — 0.4.7's top-level `pi-agent-core` had `dist/` only, `readPackageVersion()` returned null, the nested duplicate shipped, and that is how #72 happened.
- **The same overwrite install keeps a stale page cache** (#149): the package ships no `.next-desktop/server/route-cache`, but Next promotes the build's prerendered `server/app/index.html` into it on the first request and reads that copy *first* (path = route hash, no build id). After an upgrade the old UI kept loading under the new version number, and Settings › Clear cache cannot help (it clears the webview, not this server-side cache). Two guards: `NSIS_HOOK_PREINSTALL` also removes `resources\server\.next-desktop\server\route-cache`, and `desktop/server-launcher.cjs` compares `.next-desktop/BUILD_ID` with `.next-desktop/.route-cache-build-id` at startup and clears the cache (then records the id) on a mismatch or a missing marker, which heals installs that predate the hook. Pinned by `scripts/route-cache-cleanup.test.mjs`.
