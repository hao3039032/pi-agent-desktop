# Tool presets, system prompts and subagents — fork notes

Fork-owned notes moved out of `AGENTS.md` to keep it short. The upstream doc on the same topic (`docs/agents/*.md` without the `fork-` prefix) may describe the same area in other words; where they disagree, these notes describe this fork. Hard rules that must survive a merge are also listed in `AGENTS.md` under **Hard rules**.

## New session tool preset
Tool names are passed at session creation (`POST /api/agent/new` -> `toolNames[]`) and persisted in versioned `pi-web:tool-selection` custom entries. No entry means a legacy session and keeps Pi's default behavior; an empty array means Chat only. Chat only resolves before services are created, loads no extensions/skills/prompts/themes, and replaces Pi's base prompt with the ordered contents of Pi's discovered context files. Crossing the Chat-only boundary rebuilds the wrapper; changing between nonempty presets updates it in place. The composer preset chips stay a fork layer on top: for an existing session the active preset is inferred on mount via `get_tools` → `getPresetFromTools()` (see `lib/tool-presets.ts`), and the #700 guard keeps a pinned default from being rewritten by an unpinned read.

**On the CLI engine that list and that switch come from the child (bridge).** `get_tools` asks the bridge extension (`lib/pi-rpc/assets/pi-web-bridge.mjs`) for the child's real `getAllTools()`/`getActiveTools()`, and a nonempty preset change applies live through one `tools.apply` transaction (set → confirm → append the pin; a failed pin write restores the previous loadout before reporting). The child appends the pin itself, so the session file keeps a single writer. Chats and chat-only sessions, a crossing of the Chat-only boundary, or a bridge that answers no tool operations restart the child instead; a bridge protocol fault is reported through `get_tools` rather than replaced by the spawn-time list. Two differences survive: descriptions are the tool definition's (the child exposes no declared-loadout view) and `declarationHidden` stays false there. The bridge extension is attributed by `sourceInfo.path` against the shipped asset, never by command name alone.

**Live session metadata has one writer, and it is the child.** The only live metadata append the bridge offers is the enumerated `meta.scheduled-run` op (fixed `pi-web:scheduled-run` entry type, strictly validated payload in `lib/scheduled-run-marker.ts` and again in the asset, `assertIdle`, confirmed by the child's reply before the scheduled run's prompt is sent). There is no bridge op that appends an arbitrary type or payload, and none for chat unlock. Entries the host owns (the tool pin on the restart path, the chat unlock/lock entry) are written only after the child process really exited: `FileSessionManagerView` exposes only the enumerated `appendToolSelectionEntry`/`appendClearedToolSelectionEntry`/`appendChatUnlockEntry` members (its generic `appendCustomEntry` is gone), each guarded by `waitForChildExit()`. `rpc-manager.ts` additionally tracks a destroyed wrapper's real child exit (`waitForRecentChildExit`) so host appends and replacement spawns cannot race a child that is still in its exit grace — a disposed wrapper is not an exited process.

**Exact system prompts go through `before_agent_start`.** Since pi 0.86 the prompt lives in the transcript: `agent.state.systemPrompt` is a getter replayed from persisted system messages (assigning it throws), and the agent loop's request context has no `systemPrompt` field, so neither mutating the state nor patching `prepareNextTurnWithContext` reaches the model. Chat-only sessions and subagent profiles in replace mode register `lib/exact-system-prompt.ts` as an inline extension factory on the resource loader; its `before_agent_start` handler returns `{ systemPrompt }`, which the SDK projects as the provider's leading system prompt for the whole run while the transcript keeps recording Pi's structured sections. `get_state.systemPrompt` reports the exact prompt for those wrappers because the SDK state only shows the structured sections. Subagents persist their active tools plus profile-level skill and extension loading switches in `resourceSnapshot`; loaded extensions cannot expose the reserved `Agent`, `get_subagent_result`, or `steer_subagent` tools to a subagent. See `docs/adr/0002-chat-only-tool-selection.md`.

## pi ≥ 0.86: `state.systemPrompt` is read-only — project, never assign
`AgentState.systemPrompt` became a getter replayed from the transcript's system messages; assigning it throws at runtime (tsc only catches this in code typed against the real SDK — `rpc-manager.ts` goes through the structural `AgentSessionLike`, where it is invisible). Since the 2026-09-25 upstream merge the fork uses upstream's mechanism: `lib/exact-system-prompt.ts` registers a `before_agent_start` extension factory on the resource loader (see the tool-preset section above), and the fork's former `transformContext` projection (`AgentSessionWrapper.applyExactSystemPrompt()`) was deleted in its favor — do not re-add a second exact-prompt path. Stream functions take a `TranscriptContext` — fold a `Context` with `normalizeContext()` before calling one (see `lib/session-title.ts`). `lib/session-list-scanner.ts` reproduces the SDK's ordering (modified descending, then stat mtime, then reverse filename) with the same tie order upstream's `listSessionsIncremental()` implements; the summary/`detailsPending` hydration pass and the scanner's persisted index come from upstream's perf work.

## Built-in subagents
- The global `builtInEnabled` switch is persisted in `~/.pi/agent/agents/settings.json` and defaults to `false` when the file or field is absent. Malformed settings fail closed; atomic updates preserve unknown fields.
- The inline built-in extension factory is always present so reloading an existing wrapper can apply setting changes, but it registers no tools while disabled. After changing the switch, the user must explicitly reload the current session.
- LW gives the installed `pi-subagents` extension priority. `preferPiSubagentsExtension()` detects extension source/package paths (not tool names), removes the built-in host and only its resolved conflicts. The Agents settings panel disables the built-in switch and hides built-in profiles while the package is active.
- Runtime `Agent` dispatch checks the setting again, and rejects new runs only when both process-wide detection and current global package activation say pi-subagents is preferred; project-only activation must not block unrelated sessions. Existing result/steer paths remain usable.
- Preserve `findSecurityExtensionPaths()` and `registerSecurityChildExtensions()` so isolated children still inherit installed security extensions without loading unrelated ambient extensions.
- See `docs/adr/0003-built-in-subagent-toggle.md` for the precedence and persistence rationale.
- Individual built-in profiles (`general-purpose`, `explore`, `plan`) are switched off by name in the same file's `disabledBuiltIns` array, never by copying them out to a `.md` file: a copy freezes the built-in prompt at the version it was copied from and is visible to the other runtimes reading those directories. `builtInProfiles()` stamps `enabled` onto the constants so the panel, the `Agent` tool description, and `resolveSubagentProfile` agree; each write is a minimal edit that preserves names it did not touch, including ones no built-in claims (a newer build's). Reading the list fails *open* — the feature switch beside it has already failed closed — while `PATCH /api/subagents/profiles` with `scope: "builtin"` performs the write and `PUT`/`DELETE` still refuse that scope. A same-name file replaces the built-in outright and is switched off through its own frontmatter. Only the switch is live for a built-in; the rest of the form stays read-only. See `docs/adr/0005-built-in-subagent-disable.md`.
- A background run's completion notification (`notifyParent`) is skipped when the parent already collected the same result with `get_subagent_result`: the tool marks a finished background run consumed and the notification takes that mark. The check cannot happen only when the completion promise resolves — the parent is usually still inside its `get_subagent_result` poll at that moment (500ms interval) and `deliverAs: "followUp"` would just queue the duplicate until that turn ends. So `notifyParent` holds the message while the parent `isRunning()` and re-checks the mark before sending; an idle parent is still notified immediately.
- Agent profile files (`~/.pi/agent/agents/*.md`, project `.pi/agents/*.md`) are shared with other runtimes, so a save round-trips the frontmatter keys this app does not own (`name`, `allowed_subagents`, `exclude_extensions`, `disallowed_tools`, …) and carries foreign `ext:` tool selectors through. Managed keys are exactly `description`, `display_name`, `tools`, `load_skills`, `load_extensions`, `enabled`, `inherit_context`, `run_in_background`, `model`, `thinking`, `max_turns`.

## The restricted pi-subagents API and the fleet panel

- `app/api/agent/[id]/subagents` is the only surface the frontend has for the package's runs. The package speaks its public event-bus RPC (`subagents:rpc:v1`) inside the pi CHILD, where the extension is loaded — the server process has no path to that bus. The route asks the child through the bridge extension (`subagents.<method>`, `lib/pi-rpc/assets/pi-web-bridge.mjs`), which proxies exactly `ping`/`status`/`steer`/`interrupt`/`stop` over the child's `pi.events`, correlates its own request id, and answers with the package's reply body. `spawn`, `resume`, `manage` and `cost` are never forwarded (the op whitelist and the per-method parameter whitelist reject them, on both sides), so the route can never become a launch surface. `lib/pi-subagents-rpc.ts` models those five methods and the two transports (child bridge; the in-process bus stays for engines that own one). Every reply must carry `version: 1` (`parseSubagentRpcReply`/the asset's normalizer ignore anything else and let the call time out).
- **Detection is by source, never by tool name, and "unknown" is a real answer.** The old gate read `resourceLoader.getExtensions()` from the server process, which on the CLI engine has no extension list at all — every session looked "not loaded" even with the package running in the child. `piSubagentsExtensionState()` now decides from the child's own metadata (`tools.list`/`get_commands` `sourceInfo` path or package source, `pi-subagents` as a path segment or npm source), returns `unknown` when there is no metadata, and the route reports `not-loaded` only with positive evidence AND no transport. A `ping` timeout is `unresponsive`, an older bridge without the ops is `unknown` (`SubagentRpcUnsupportedError`), neither is "reinstall the package".
- The proxy does **not** wait for an idle session: the fleet polls status and steers exactly while a run is going, and pi dispatches extension commands immediately even during streaming (docs/rpc-commands.md), so the prompt channel is safe mid-run. Host and child both bound the whole exchange (child 20s default / 30s cap, host request timeout), the listener is removed when the wait ends, and a 2 MB result cap keeps an oversized transcript out of a notify line.
- `lib/pi-subagents-view.ts` is the bounded projection: run rows from the `asyncSnapshot` tree (background runs only), the `fleetSummary` from the fleet DTO (the only place foreground children of the running `Agent` tool appear — display rows, no run ids, never controllable), plus `summaryText`, capability flags and drop counters. Unknown states stay `unknown`; a disconnected run is never reported finished.
- Steering targets **run ids only**. The async snapshot carries no authoritative child indexes (the package's own `status.steps` ordering is what steer's `index` means, and the snapshot merges steps, graph stages, nested children and host steps into one display list), so a display offset must never be sent as one. A child-scoped stop sends the `childId` the package reported (`workflowKey`/`runId`/`step:N` are its own identity candidates; `resolveAsyncStatusChild` resolves them server-side).
- The route re-probes (`ping`) before every call: GET degrades to `{ available: false, reason }` (200) so polling stays cheap; POST answers transport failures with 4xx/5xx, refuses actions the bridge did not advertise (400 `capability-unavailable`) and never forwards `dir`/`path`/arbitrary params. Run ownership stays the package's own `ownsRun` check — a foreign run id comes back `not_found` (404).
- In-flight RPC is bound to the wrapper's lifecycle (`getLifecycleAbortSignal()`): when the wrapper starts closing, the call aborts and the route answers `session-closed` (GET 200 / POST 409) instead of hanging to its timeout.
- The desktop UI surface is `components/SubagentFleetPanel.tsx`, opened by clicking the existing composer widget tags `subagent-fleet-status` / `subagent-async` in `ExtensionWidgets`. It replaces the inert terminal snapshot (whose arrow-key hints cannot work in the browser) inside that tag's expanded panel; there is no dedicated workspace tab or extra More-menu entry. Other widgets keep their text renderer. The tag starts collapsed; expanding mounts the native panel, collapsing cancels requests and stops polling. Session-keyed widget groups prevent an old session's expanded controls from leaking into another. Chats do not receive the fleet session id. The panel offers output, steer, interrupt and stop controls with server-computed flags and keeps the fleet summary display-only (it mixes foreground/background work and cannot be subtracted from tree-row counts). A child-scoped stop is offered only for a top-level child of a run: the package's stop resolves the `childId` against that run's top-level steps only (`resolveAsyncStatusChild` without `includeNested`), so a nested child is not addressable and gets no Stop button. `npm run test:subagent-fleet` drives the panel in a browser (tag expansion, the four actions, collapse, session isolation, mobile width, height cap, Escape).
- A background run's completion reaches the parent through `sendCustomMessage`, and pi's `convertToLlm` replays every `custom` message to the model as a plain `user` turn. `subagentNotificationText()` therefore prefixes the report with `SUBAGENT_NOTIFICATION_PREFIX` so a compaction pass — whose prompt asks what *the user* wants — does not file the subagent's output under Goal / Constraints (#875). Foreground `Agent` and `get_subagent_result` results keep the bare `subagentFinalText()`: they are already `toolResult` messages and need no marker. Keep the prefix in code, not in a profile prompt, so the model cannot drop it.
- The `skills` / `extensions` spellings pi-subagents reads are seeded on first save and kept in step while they are booleans; a hand-authored whitelist such as `extensions: pi-advisor-flow` is never rewritten, and the two flags fall back to those aliases when `load_skills` / `load_extensions` are absent.
